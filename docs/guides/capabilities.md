# Возможности и границы

## Задача

Для распределённого HTTP-запроса трудно понять, где возникла ошибка или
задержка и не усиливают ли проблему повторы. ZeroTrace объединяет просмотр
наблюдаемых цепочек, аудит retry/timeout-политик и проверку изменений в
управляемом эксперименте.

Исходная идея сосредоточена на диагностике ошибочных и медленных цепочек.
Текущая реализация добавляет числовое объяснение конфигурационных проблем
и лабораторию для реального повторного выполнения запросов.

## Что делает приложение

| Возможность | Как работает | Граница |
|---|---|---|
| Трейсы и связи сервисов | OTLP/HTTP → нормализация → SQLite → дерево, временная шкала и граф | Источник должен экспортировать телеметрию; видны только наблюдаемые операции |
| Аудит | Сопоставляет попытки, тайминги и доступные снимки политик; возвращает основания и рекомендации | Отсутствующие настройки не выдаются за известные; правила имеют критерии пригодности данных |
| Числовая рекомендация | Например, проверяет `N × timeout + (N−1) × backoff` относительно родительского бюджета | Формула относится к последовательным попыткам и фиксированной паузе; не универсальный прогноз всей системы |
| Изменение настроек | Зарегистрированный HTTP-адаптер, разрешённые поля, план, подтверждение, ревизии, request_id и readback | Один план относится к одной цели; автоматической транзакции по всем сервисам нет |
| Лаборатория | Реальные HTTP-процессы, задержки, ошибки, нагрузка и OTLP | Готовый checkout — контролируемый пример, а не копия произвольной пользовательской системы |
| Сравнение прогонов | Полные снимки конфигураций, seed, сценарий/fault и зафиксированные ревизии трейсов | Требуется сопоставимость; произвольные два прогона могут быть отклонены |
| Прогноз ускорения | Интерфейс отправляет точную ревизию трейса и сокращения выбранных веток в серверный API проекции и показывает его результат | Прогноз не измерен запуском и не моделирует новый трафик, retries, кэш и побочные эффекты |
| Сравнение групп | Интерфейс передаёт серверу две группы точных ревизий трейсов одного эндпоинта; сервер вычисляет статистики и различия | Различия выборок не доказывают причинность |
| Отчёты | Сервер формирует JSON/HTML и сохраняет ссылки на входы расчётов | Наличие API не означает отдельный экран для каждой функции |

## Наблюдение и управление

Прогноз и сравнение групп описаны в [руководстве по анализу трейсов](trace-analysis.md).
Для временных расчётов пользователь отвечает за согласованность часов источников.
Сервер использует полученные временные отметки; отсутствие `clock_domain` само
по себе не блокирует расчёт. Проверки структуры, потерь и фактических временных
границ сохраняются.

Это возможности конкретного сервиса, а не обязательный режим всей системы.
Любой подключённый источник может наблюдаться. Читать или менять настройки
можно только при наличии зарегистрированного совместимого адаптера.

В поставляемом `shop` ручные изменения разрешены у `orders` для timeout,
числа попыток, паузы и условий повтора. `payment` и остальные приложения
используются для наблюдения. В лаборатории управляются все сервисы сценария.
Рекомендации применяются только к поддерживаемым целям лаборатории.

Успешная запись `applied` означает, что сервер подтвердил действующий конфиг.
Она сама по себе не подтверждает исчезновение ошибки или ускорение запросов.
Эффект проверяется отдельной выборкой данных или сопоставимым прогоном.

## Что не следует обещать

- Встроенное подключение к любым процессам без настройки SDK/инструментации.
- Наличие собственного eBPF-агента или установки OpenTelemetry в приложения из UI.
- Восстановление всей системы и её поведения по одному трейсу. Генератор
  сейчас поддерживает линейную цепочку; готовый checkout поддерживает ветвления.
- Автоматическое изменение конфигураций любого внешнего сервиса.
- Гарантированное ускорение по расчётному прогнозу или причинный вывод по двум группам.
- Реализацию всех пунктов долгосрочного плана. В частности, исходный механизм
  хранения только проблемных трейсов с ограничением по TTL/объёму не входит
  в текущий путь записи принятых spans.
- Подтверждённую производственную масштабируемость или нативную поддержку
  всех ОС по результатам локального Docker-запуска.
