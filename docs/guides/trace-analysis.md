# Прогноз ускорения и сравнение групп трейсов

Это два разных способа исследовать уже полученную телеметрию. Интерфейс задаёт
входы расчёта и отображает результат сервера. Метрики и экспортированный результат
не пересчитываются отдельным браузерным алгоритмом.

## Прогноз ускорения одного запроса

В карточке трейса откройте «Прогноз ускорения», выберите ветку вызовов и укажите,
на сколько процентов сократить её длительность. Сервер пересчитывает длительность
всего запроса с учётом последовательных и пересекающихся во времени веток.
Ускорение одной параллельной ветки может не сократить весь запрос, если другая
ветка продолжает определять время ожидания.

`POST /api/v1/projections` получает `trace_ref` с окружением, trace ID, поколением
и ревизией, а также `changes`: список `span_id` и `speedup_percent`. Опциональный
`root_span_id` ограничивает расчёт поддеревом. Результат содержит исходную
длительность, прогноз, выигрыш, кандидатов на ускорение, допущения, ограничения
и `analysis_id`. При изменении выбора UI ожидает новый ответ сервера; устаревший
ответ не становится результатом нового сценария.

Если данных недостаточно, сервер возвращает причину вместо выдуманного выигрыша.
Например, отсутствующий родитель, потерянные данные, цикл или существенно
выходящий за границы родителя дочерний интервал препятствуют расчёту.

Прогноз не выполняет приложение заново и не моделирует новую нагрузку, изменения
числа повторов, кэширование или побочные эффекты. Проверка изменения реальным
запуском выполняется в лаборатории отдельно.

## Временная шкала

Пользователь, подключающий источники, обеспечивает согласованность их временных
отметок. Прогноз и сравнение интервалов считают переданные timestamps одной
временной шкалой. Отсутствие или различие `clock_domain` не означает автоматический
отказ и не заменяется придуманной меткой часов. Исходные timestamps сохраняются.
Это допущение модели, а не результат измерения или автоматической синхронизации
часов ZeroTrace. Невозможные фактические границы всё равно проверяются.

## Сравнение двух групп запросов

В списке трейсов нажмите «Сравнить» и выберите запросы в группы A и B. В обеих
группах должны быть запросы одного входного эндпоинта одного сервиса и окружения.
Например, можно вручную выбрать запросы `/checkout`, наблюдавшиеся до релиза
и после него. На каждую группу сервер принимает от 1 до 100 точных `TraceRef`.
Один и тот же запрос не может находиться в обеих группах, даже с разными ревизиями.

`POST /api/v1/comparisons` принимает `baseline_trace_refs` и
`candidate_trace_refs`. Сервер сравнивает количество запросов, медиану и p95
длительности, ошибки входного запроса и внутренних вызовов, доступные показатели
обращений к зависимостям. Возвращаются различия, сведения о покрытии данных,
предупреждения и `analysis_id`. Неподходящие группы отклоняются; пропавшие
ревизии нельзя молча исключать из расчёта.

Разница между группами сама по себе не устанавливает причину. У запросов могли
отличаться входные данные, нагрузка, состояние зависимостей или версия сервиса.
Маленькая выборка и неизвестные сведения о нагрузке отмечаются в результате.

## Отличие от лабораторного сравнения

Группы трейсов пользователь выбирает из наблюдаемого трафика. Лабораторное
сравнение получает `baseline_run_id` и `candidate_run_id` и использует
зафиксированные выборки двух прогонов. Оно дополнительно проверяет сценарий,
сбой, нагрузку, seed и снимки конфигураций: должен измениться один поддерживаемый
параметр политики. Оба варианта используют сервер, но имеют разные входы и
условия сопоставимости.

## Воспроизводимость результата

Серверные расчёты привязаны к точным ревизиям трейсов и сохраняют `analysis_id`.
Скачанный из интерфейса JSON содержит серверный результат. Серверный отчёт может
включать сохранённые результаты по `projection_id` и `comparison_id`; подробности
API приведены в [операторском руководстве](operations.md).

## Что изменилось

Раньше интерфейс отдельно вычислял прогноз и статистики групп, хотя аналогичные
расчёты уже существовали на сервере. Теперь обе вкладки используют серверные API;
локальные `projectIntervals`, `cohortStats` и `compareCohorts` удалены. Числа,
кандидаты на ускорение и экспортируемый результат поступают из одного расчёта.

Раньше серверный прогноз отказывал обычным OTLP-трейсам без подтверждённого
`clock_domain`. Теперь согласованность timestamps — явное допущение, за которое
отвечает пользователь источника. Проверки структуры и фактических границ
сохранены. Версии алгоритмов повышены до `interval-blocks-v1.1.0` для прогноза
и `1.1.0` для групп, чтобы результаты с разными допущениями различались.

При изменении входов интерфейс отменяет предыдущий запрос и скрывает устаревший
результат. Отрицательная разница медиан принимается корректно: группа B может
оказаться быстрее A. В режиме локальных демоданных предлагается подключить
сервер, а вычислительная подстановка не выполняется.

## Как проверяется интеграция

- [Тест публичного API](../../backend/tests/analytics/test_common_analytics_api.py)
  проходит от HTTP OTLP-приёмника без clock metadata до числового прогноза.
- [Тесты клиентского контракта](../../frontend/tests/analytics-client.test.ts)
  проверяют точные ревизии в POST-запросах, сохранение серверного ответа,
  отрицательную разницу, отказ сервера, некорректный ответ и отмену запроса.
- [Серверные тесты прогноза](../../backend/tests/analytics/test_projection.py) и
  [сравнения](../../backend/tests/analytics/test_comparison.py) проверяют математику,
  параллельные интервалы, качество данных и условия сопоставимости.

Для проверки работающего приложения откройте прогноз по настоящему трейсу,
добавьте ветку и убедитесь, что отправлен `POST /api/v1/projections`. Затем
выберите две группы в списке и получите `POST /api/v1/comparisons`. Скачанные
JSON должны содержать те же метрики и `analysis_id`, что вернул соответствующий
API-запрос. Полные команды автоматических проверок приведены в
[руководстве по тестированию](../development/testing.md).
