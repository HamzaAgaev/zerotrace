# Сценарий тестового стенда

Стенд запускает изолированные HTTP-моки по явному JSON. Реальные сервисы и трейсы не используются для подбора параметров или восстановления поведения.

1. Откройте «Тестовый стенд».
2. Нажмите «Загрузить JSON» и выберите файл. Сервер проверит его и покажет сводку без запуска процессов. Рабочий пример доступен по кнопке «Скачать пример JSON».
3. Нажмите «Создать стенд». Некорректная схема отклоняется до запуска процессов.
4. Выберите сервис на схеме, настройте задержки, повторы или имитацию ошибок. Запустите тест и откройте его результаты.

Полный пример: [example.json](../../stand/scenarios/example.json). В нём `api` параллельно вызывает `worker-a` и `worker-b`, затем ещё раз вызывает `worker-a`. `worker-b` отвечает 503, вызывающая сторона делает две попытки. Вызов необязательный, поэтому основной запрос заканчивается 200. Это позволяет увидеть внутренние ошибки и повторы при успешном итоговом ответе.

## Формат

- `schema_version`: строка `"1"`.
- `scenario_id`: название сценария из латинских букв, цифр, `_` и `-`.
- `scenario_revision`: положительное целое число.
- `entrypoint`: `service_id` и `route` вида `POST /run`. Сюда отправляется нагрузка.
- `services`: объект, ключи которого — идентификаторы сервисов. Каждый содержит `routes`.
- Ключ `routes` — метод и путь, например `GET /work`.
- Для каждого эндпоинта обязательны `work`, `response_status`, `calls`, `steps`.
- `work`: собственное время обработки, **без времени других сервисов**. Либо `{"kind":"fixed","delay_ms":10}`, либо `{"kind":"lognormal","p50_ms":10,"p99_ms":40}`.
- `response_status`: окончательный HTTP-код при завершении всех шагов.
- `calls`: именованные вызовы. Каждый содержит `target` (`service_id`, `method`, `route`), `timeout_ms`, `max_attempts` (включая первую), `backoff_ms`, `retry_on` и `required`.
- `retry_on`: массив кодов (`"503"`) или категорий (`"4xx"`, `"5xx"`, `"timeout"`, `"connect"`). Пустой массив запрещает повторы по ошибке.
- `required: true`: окончательная ошибка этого вызова прерывает дальнейшие шаги и становится ответом текущего сервиса. При `false` выполнение продолжается.
- `steps`: последовательный массив шагов с уникальным `id`. `call` задаёт один вызов, `parallel` — список одновременно выполняемых вызовов. Следующий шаг начинается после завершения всей группы. Один call можно явно повторить в разных шагах.
- Необязательный `delay_ms` шага — пауза до его начала (по умолчанию 0). `offsets_ms` — задержки старта отдельных участников группы (по умолчанию 0). `tail_ms` эндпоинта — пауза после всех шагов (по умолчанию 0).
- Пустые `calls: {}` и `steps: []` явно описывают конечный сервис.

В каждом маршруте можно задать `fault`: `error_rate` от 0 до 1, `http_status` 400–599, `delay_ms` и `failure_point`. Пример точки: `{"mode":"fixed","boundary_id":"before-first"}`. Доступны также `after-<id шага>` или случайный выбор `{"mode":"random","boundary_ids":["before-first","after-work"]}`. Если fault отсутствует или равен null, имитация ошибок выключена. Её можно настроить через интерфейс после запуска.

## Границы модели

Схема задаёт HTTP-вызовы, а не бизнес-логику приложения. Условия по содержимому ответа, базы данных и произвольный код не воспроизводятся. Циклы графа маршрутов отклоняются; обращения A → B → A допустимы, если маршруты различаются и цикла нет. Повторы выполняются по политике max_attempts. Поддерживаются до 32 сервисов, 256 эндпоинтов суммарно и 256 шагов/вызовов в эндпоинте, до 64 участников параллельного шага. Одна политика повторов на целевую операцию одного сервиса; конфликтующие определения отклоняются.

Повторный импорт всегда использует настройки из файла и не восстанавливает настройки прошлого стенда. Черновик JSON сохраняется в браузере. Старые результаты тестов остаются доступными. Демо в браузере показывает тот же интерфейс, но результаты в нём иллюстративные; для выполнения HTTP-сценария подключите сервер.

## Сценарий окружения

В серверном конфиге задайте `environments[].lab_scenario_file`. Например:

```json
{"environments":[{"environment_id":"shop","kind":"external","lab_scenario_file":"scenarios/shop.json"}]}
```

Относительный путь считается от каталога основного конфига. Для программного `create_app` задайте `config_directory`, иначе используется рабочий каталог процесса. В Compose папка `stand/scenarios` монтируется read-only в `/config/scenarios`; пример `shop` связан с полноценным `checkout.json` из девяти сервисов.

Файл читается при запуске сервера. Во вкладке «Сервисы» появляется кнопка «Создать тестовый стенд», даже если трейсы ещё не поступили. Ошибка файла отключает создание стенда, но не мониторинг. Изменённый файл перечитывается при перезапуске. Браузер не передаёт серверные пути.

## Проверка и снимки

[JSON Schema v1](../../stand/scenarios/scenario-v1.schema.json) описывает структуру. Дополнительно сервер проверяет ссылки, циклы, границы ошибок и согласованность политик. Неизвестные поля, в том числе observed_*, запрещены. Размер JSON — до 1 МиБ.

`POST /api/v1/lab/scenarios/validate` принимает ровно один из объектов: `{"scenario": {...}}` или `{"environment_id":"shop"}`. Возвращает нормализованный scenario, scenario_hash (SHA-256), scenario_id, scenario_revision, service_count и route_count в envelope `lab-scenario`.

`POST /api/v1/lab/stands` принимает один selector: `scenario_hash`, `environment_id` или встроенный `scenario_id: "checkout"`; дополнительно разрешён request_id. Синтаксические ошибки и неправильный selector дают 400, неизвестный hash — 404, неверный сценарий — 422 с errors/path, превышение размера — 413. Создание по source отвергается с unsupported_stand_source.

Оба способа используют одно хранилище неизменяемых снимков SQLite. Порядок ключей, численно одинаковые значения и пропущенные необязательные нули не меняют hash. Изменение поведения или ревизии меняет hash. Стенды и результаты хранят hash и происхождение сценария. Новый стенд всегда начинает с JSON, не с изменённых настроек предыдущего стенда.

## Воспроизводимость

Необязательное поле seed нагрузки принимает целое от 0 до 9007199254740991. Пустое значение выбирается сервером и сохраняется в результате. Кнопка «Использовать seed» переносит его в следующий тест. Seed повторяет случайные решения модели, а не точные сетевые длительности.

Вероятность ошибки разыгрывается для каждого запроса. После срабатывания случайная граница выбирается равновероятно из boundary_ids. Ошибка обязательной зависимости завершает обработку раньше последующих шагов и ошибок; ошибка необязательной сохраняется в телеметрии, но не останавливает обработчик. Каждое исполнение шага имеет собственный logical_call_id; только попытки этого исполнения разделяют один идентификатор.

Прогноз ускорения и сравнение тестов в интерфейс не возвращаются. История старых тестов остаётся доступной; старые стенды из трейсов не восстанавливаются автоматически.
