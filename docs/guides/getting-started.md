# Сборка и запуск

## Окружение

Рекомендуемый способ — Docker Compose. На хосте нужны Git, работающий Docker
и Compose v2 (`docker compose version`). Порт `127.0.0.1:8000` должен быть свободен.
Первый build скачивает базовые образы и зависимости из реестров.

Контейнеры используют Python 3.12 и Node.js 22. Node нужен только при сборке UI;
запущенный сервер раздаёт готовые файлы. Для разработки вне контейнера backend
объявляет Python ≥3.11, frontend — Node.js 22, но инструкция ниже не требует
устанавливать их на хост.

## Система с готовым примером

```sh
git clone https://github.com/HamzaAgaev/zerotrace.git
cd zerotrace
docker compose --profile demo up --build -d
docker compose --profile demo ps
```

Откройте http://127.0.0.1:8000. Работают 11 контейнеров: ZeroTrace, девять
приложений и `demo-load`. У сервера и приложений настроены healthchecks;
у генератора нагрузки отдельного healthcheck нет.

Девять приложений — gateway, orders, inventory, pricing, delivery, payment,
fraud, bank-api и notifications. Они образуют пример внешней системы `shop`.
Генератор нагрузки выполняет просмотр товара, оформление заказа и возврат.
Первые трейсы появляются после готовности приложений и очередного запроса.
Бизнес-порты demo-сервисов доступны внутри Compose-сети; на хост опубликован
только UI/API ZeroTrace.

Для управляемого эксперимента откройте «Лабораторию» и нажмите
«Создать стенд оформления заказа». Сервер запустит отдельные процессы девяти
сервисов внутри своего контейнера. Это окружение `sandbox`; оно отделено
от внешнего demo. Нагрузка запускается отдельным действием пользователя.
[Пошаговое демо](demo-checklist.md).

## Только ZeroTrace и собственные приложения

```sh
docker compose up --build -d
```

Собственные приложения запускает пользователь. Для их наблюдения настройте
OTLP exporter или совместимую инструментацию. Источник и его окружение
регистрируются в `deploy/config.json`; для read/write config дополнительно
нужен адрес управляющего адаптера. [Подключение и API](operations.md).

Встроенного агента, автоматически подключающего любые процессы, нет.
OpenTelemetry Collector можно использовать отдельно; для прямой отправки
OTLP/HTTP в ZeroTrace он не обязателен.

## Повторный запуск, обновление и данные

```sh
docker compose --profile demo stop             # остановить
docker compose --profile demo up -d            # запустить существующий образ
```

После изменения исходников образ нужно пересобрать:

```sh
docker compose --profile demo stop
git pull --ff-only
docker compose --profile demo up --build -d
```

Именованные volumes содержат SQLite, токены источников и настройки demo-сервисов.
Обычные `stop` и `down` их сохраняют. `down -v` удаляет данные; для штатного
перезапуска эта команда не нужна. История лабораторных прогонов сохраняется,
но после перезапуска сервера лабораторию нужно запустить явно.

Compose публикует порт только на loopback: доступ с других компьютеров
потребует отдельной настройки развёртывания. Инструкция описывает локальный
запуск; native-совместимость на всех ОС и многопользовательское production
развёртывание не являются подтверждёнными свойствами этой поставки.

## Диагностика запуска

```sh
docker compose --profile demo ps
docker compose logs --tail=100 zerotrace
docker compose --profile demo logs --tail=50 demo-load
```

Если порт занят, сначала остановите его владельца или настройте публикацию
порта в `compose.yaml`. При изменении host-порта сохраните внутренний адрес
экспортёров `http://zerotrace:8000/v1/traces`.

Не очищайте volumes при обычной ошибке подключения. Логи предназначены для
локальной диагностики; не публикуйте токены и пользовательские данные.

## Зависимости и проверки

Docker устанавливает Python-зависимости из `deploy/requirements.lock`, UI —
через `npm ci` из `frontend/package-lock.json`. `deploy/requirements.txt`
перечисляет прямые зависимости, а `backend/pyproject.toml` описывает Python-пакет;
они не подменяют lock-файлы Docker-сборки.
