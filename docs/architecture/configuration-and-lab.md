# Подключение, конфигурация и лаборатория

Система наблюдает реальные HTTP-вызовы и отдельно управляет сервисами,
для которых зарегистрирован конфигурационный адаптер. Возможность изменения
определяется для каждого сервиса и каждого поля. Полный целевой объём описан
в [плане](../plans/PLAN.md); устройство модулей — в [components.md](components.md).

## Запуск

Один Python-сервер объединяет управление, данные и аналитику и раздаёт
собранный UI с того же origin. Docker Compose запускает сервер и,
по выбранному профилю, демонстрационные приложения.

Сервер читает реестр источников и адаптеров при старте. Токен экспортёра
сопоставляется с источником и окружением. Адрес управляющего API и права
по полям отдельно регистрируются по ключу сервиса. Топология наблюдения
восстанавливается из телеметрии. Адрес управления берётся из реестра.
Примеры используют отдельные окружения `shop` и `sandbox`.

Пример пользовательской системы запускается отдельным Compose-профилем
`demo`. Он содержит девять приложений и `demo-load`, который создаёт
поток запросов. Реальные пользователи запускают собственные приложения
с настройками OTLP. Модуль управления запускает лабораторные процессы по действию оператора.

## Пример системы и сценарий

Внешний пример и готовый лабораторный checkout включают gateway, orders,
inventory, pricing, delivery, payment, fraud, bank-api и notifications.
Orders параллельно проверяет остатки, цену и доставку, затем выполняет оплату
и уведомление. Payment последовательно обращается к fraud и bank-api.
Внешний пример также содержит просмотр цены/остатков и возврат денег.
У операций оплаты и возврата отдельные исходящие политики.

Сценарий задаётся версионированным файлом. Маршрут содержит последовательные
шаги, шаг может состоять из параллельной группы. Обязательный вызов после
исчерпания попыток останавливает дальнейшие шаги. Уже запущенная группа
дожидается завершения. Notifications необязателен, ошибка видна в трейсе,
а заказ остаётся успешным. HTTP-ошибка обязательного вызова возвращается
тем же статусом, таймаут даёт 504, ошибка соединения — 502.

## Конфигурация

Действующий конфиг принадлежит сервису. Модуль управления использует адаптер с операциями
чтения, условной записи и проверки результата по request_id. Для первого
адаптера используются `GET /_config`, `PATCH /_config` и
`GET /_config/operations/{request_id}`. Планирование и журнал находятся на сервере ZeroTrace.

Политика исходящего вызова определяется вызывающим сервисом, адресатом,
методом и маршрутом. Предыстория входящего запроса на выбор политики не
влияет. У политики стабильный `call_ref`. Настраиваются таймаут попытки,
максимальное число попыток с первой, пауза и условия повтора. Ответ сервиса
содержит `write_fields`; Сервер учитывает также разрешения своего реестра.

Для входящего маршрута стенда задаётся собственная работа `fixed` либо
`lognormal` с p50/p99. Время дочерних запросов добавляется при реальном
исполнении. Дополнительная задержка сбоя задаётся отдельно. Логнормальный
профиль имеет два редактируемых квантиля.

Сервис фиксирует конфиг в начале входящего запроса. Все его шаги используют
один снимок. Новая ревизия действует для новых запросов. При ручном
редактировании внешнего сервиса трафик может продолжаться. На стенде
редактирование запрещено во время выполнения нагрузки.

## План и применение

1. Интерфейс читает сервисы, возможности и действующий конфиг у сервера.
2. Интерфейс отправляет `POST /api/v1/change-plans` с окружением, сервисом,
   call_ref или входящим маршрутом, ожидаемой ревизией и изменениями.
3. Сервер проверяет доступ, значения и ревизию, сохраняет план с before/after,
   хешем и сроком действия.
4. Оператор подтверждает его. Интерфейс отправляет request_id и plan_hash в apply.
5. Сервер сохраняет журнал до записи. Сервис атомарно проверяет ревизию и весь
   набор полей, обновляет конфиг и сохраняет результат request_id.
6. Сервер перечитывает конфиг и подтверждает applied. При потерянном ответе
   уточняет результат по request_id. Неопределённость отображается как
   unknown. Новая запись требует нового плана по актуальному конфигу.

Один план меняет несколько полей одной цели. У каждого сервиса собственная
ревизия. Повтор request_id с тем же содержимым возвращает прежнюю операцию,
с другим — 409. Устаревшая ревизия также даёт 409. Применение аналитической рекомендации
доступно на стенде. Ручные разрешённые правки внешнего сервиса доступны
отдельно. Аналитика получает снимки политик с длительностями в наносекундах.

## Сбои и прогоны

Сбой относится к входящему маршруту. Настраиваются вероятность на каждое
обращение, код ошибки, дополнительная задержка и граница исполнения.
Граница выбирается явно либо равновероятно из отмеченных точек при
срабатывании ошибки. Примеры — до первого шага, после проверки fraud,
после bank-api. Граница параллельного шага находится после всей группы.
Если обязательный вызов завершил маршрут раньше выбранной границы,
результат этого вызова сохраняется.

Запуск принимает request_count, concurrency и необязательный seed.
При отсутствии seed сервер генерирует его. Фактическое значение возвращается
и сохраняется. Seed относится к моделированию стенда. Обычный адаптер
пользовательского сервиса не обязан его поддерживать.

Прогон фиксирует scenario_revision, fault_revision и config_revisions всех
сервисов вместе с полными снимками. Сервер сверяет их перед запуском. Нагрузка
порождает реальные HTTP-запросы. Состояние выполнения отделено от состояния
сбора трейсов. HTTP 503 является результатом эксперимента. Хранилище фиксирует
выборку waiting/ready/partial по run_id. Пробные запросы помечаются probe
и исключаются из выборки. Сравнение использует сохранённые выборки и
проверки сопоставимости аналитического модуля.

После перезапуска сохраняются история, планы, результаты и настройки.
Прерванный прогон получает failed. Контроллер завершает подтверждённо принадлежащие
ему процессы старого стенда, оператор запускает лабораторию из сохранённых
настроек. Автоматический откат и межсервисная транзакция — последующие задачи.

## Генератор и граф

Готовый checkout поддерживает последовательные и параллельные вызовы.
Генератор из выбранной ревизии трассы реализован для линейной цепочки.
Для ветвления, неоднозначных связей или других неподдерживаемых структур
он возвращает объяснение отказа. Генерация произвольного графа не реализована.
Наблюдаемые значения и подставленные defaults показываются с происхождением.
Исходные внешние адреса не используются для запросов лаборатории.

Необязательное `SpanView.target` переносит наблюдаемый адресат клиентского
спана в API. При отсутствии парного server-спана интерфейс показывает отдельный
узел зависимости. На ребре используется клиентский интервал. Идентичность
узла адресата отделена от сервиса с совпадающим именем. Доступ к управляющему
API берётся из реестра. Дополнительная подпись на узле не требуется.
