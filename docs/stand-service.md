# Шаблон сервиса стенда

`stand.service` запускает один HTTP-сервис из [checkout](../scenarios/checkout.json).
Один и тот же процесс используется дочерними сервисами лаборатории и контейнерами
внешнего демонстрационного профиля.

```text
python -m stand.service \
  --scenario scenarios/checkout.json \
  --service-id payment \
  --port 18084 \
  --state-dir data/payment \
  --urls data/service-urls.json \
  --endpoint http://zerotrace:8000/v1/traces \
  --lab
```

`--urls` содержит JSON-объект `service_id → base URL`. В лаборатории A
создаёт этот файл с loopback-портами. В Compose сервисы используют DNS-имена.
`--lab` разрешает изменять конфиги всех сервисов. Внешний профиль использует
поле `config_write` из сценария, поэтому запись разрешена только `orders` и
`payment`.

Процесс также принимает `POST /_shutdown` для завершения подтверждённо
принадлежащего A процесса после перезапуска управляющего сервера. Управляющие
маршруты `_config`, `_health`, `_chaos`, `_flush` и `_shutdown` исключены из
Flask- и requests-инструментации.

## Конфигурация

`GET /_config` возвращает ревизию конфигурации сервиса, `routes` с
собственной задержкой обработки и разрешёнными границами сбоя, а также
плоский список `calls`. Исходящий вызов идентифицируется стабильным
`call_ref` и одним правилом для адресата, метода и маршрута.

`PATCH /_config` принимает:

```json
{
  "request_id": "change-42",
  "expected_revision": "3",
  "call_ref": "bank-authorize",
  "set": {"timeout_ms": 500, "max_attempts": 3}
}
```

Или вместо `call_ref` можно передать `route` и
`set: {"work":{"kind":"lognormal","p50_ms":20,"p99_ms":60}}`.
Сервис проверяет версию, изменяет все переданные поля вместе и сохраняет
результат по `request_id`. Повтор того же запроса возвращает тот же результат,
а другой запрос с этим идентификатором получает `409`. Результат читается из
`GET /_config/operations/{request_id}`.

`PUT /_chaos` принимает правило выбранного входящего маршрута с `route`,
`error_rate`, `http_status`, `delay_ms` и `failure_point`. Точка бывает
фиксированной по `boundary_id` или случайной по `boundary_ids`. `DELETE
/_chaos` очищает правила, либо сбрасывает правило одного маршрута при
передаче `route`.

## Исполнение маршрута

В начале запроса сервис фиксирует снимок своей конфигурации. `work` задаёт
собственную задержку маршрута, а не полное время ответа. Последовательные
шаги и параллельные группы находятся в `steps`. После неуспеха обязательного
вызова сервис ждёт оставшуюся часть уже начатой группы и прекращает следующие
шаги. HTTP-ошибка передаётся наверх, таймаут превращается в `504`, ошибка
соединения в `502`. Необязательный вызов остаётся в трейсе и не меняет ответ
маршрута. Успешный маршрут возвращает `response_status` из сценария, по
умолчанию `200`; допустим любой HTTP статус от `100` до `599`. Любой ответ
исходного вызова в диапазоне `2xx`, включая `201` и `204`, считается успехом.

С `--endpoint` сервис включает Flask и requests OpenTelemetry
инструментацию. `ZEROTRACE_OTLP_TOKEN` или `--token-file` передаёт заголовок
Authorization экспортёру. Входящие `X-ZeroTrace-Run-Id`,
`X-ZeroTrace-Seed`, `X-ZeroTrace-Request-Index` и `X-ZeroTrace-Probe`
распространяются по вызовам. Клиентский спан каждой попытки содержит
`zerotrace.call_ref`, стабильный `zerotrace.logical_call_id`,
`zerotrace.attempt_index` и `http.request.resend_count`.
Для лабораторной нагрузки ключ моделирования строится из seed, индекса
входящего запроса, пути ветки и номера попытки. Поэтому изменение числа
попыток не сдвигает случайные значения других запросов.
