## 1. Что должно работать

1. Внешний источник отправляет OTLP; внешний девятисервисный пример запускается Compose-профилем `demo`.
2. A создаёт лабораторный checkout по готовому `scenario_id`; запросы и телеметрия стенда идут через отдельное окружение.
3. Оператор настраивает route-scoped fault, запускает повторяемые прогоны с одинаковой нагрузкой и сопоставляет результаты.
4. A владеет планом и применением целиком. Сервисный adapter поддерживает GET/PATCH конфигурации и readback/status по request_id; рекомендации разрешены только для лабораторной цели.

## 2. Компоненты и владельцы

Один Python-бэкенд, одна SQLite и три серверных модуля. HTTP-роутеры подключаются к общему приложению. Тестовые HTTP-сервисы запускаются как дочерние процессы. Первый профиль использует Flask и requests с автоинструментацией OpenTelemetry из текущего плана.

| Владелец | Обязанности | Стык с командой |
|---|---|---|
| Никита | Запуск приложения, реестр источников и адаптеров, конфиги, планы и журнал, супервизор стенда, сбой и нагрузка | Владеет планированием и применением целиком; получает намерение рекомендации от Амира. Владеет состоянием прогона и сроком ожидания телеметрии. Отдаёт Хамзе статусы стенда и операций. |
| Миша | OTLP, SQLite, граф, ревизии, API трасс и сервисов, извлечение цепочки, фиксация выборок по run_id | Отдаёт Никите последовательную цепочку и причины отказа в сборке. Отдаёт Амиру граф, попытки и зафиксированные выборки. |
| Амир | Диагностика, рекомендации, аудит, проверка сопоставимости и сравнение | Использует сохранённые наблюдения и конфиг с указанным источником. Возвращает Хамзе расчёт, ограничения и результат сравнения. |
| Хамза | Потребитель API и координатор интеграции | Проверяет UI по общим примерам, затем на реальных ответах трёх модулей. |

## 3. Как работать параллельно

В начале один раз сверяем форматы ниже и сценарий из P11. После этого каждый запускает свой модуль локально с тестовой реализацией соседнего интерфейса. Заглушки используются в тестах и деморежиме. При интеграции меняется поставщик данных, а сценарий и форматы остаются теми же. Для каждого стыка производитель проверяет свои ответы на общем примере, потребитель проверяет чтение того же примера.

| Кто работает | Что использует до интеграции | Что сдаёт для подключения |
|---|---|---|
| Никита | Проверенная цепочка из JSON и пример рекомендации R4. Сервисы стенда можно запустить локально и проверить через HTTP без аналитики и базы коллег. | Генератор, управление конфигом, запуск и остановка. Для прогона публикует метаданные с версиями сценария, сбоя, нагрузки и снимком конфига. |
| Миша | Записанный пакет OTLP или контролируемый тестовый пакет с теми же спанами и run_id. Запускает ingest и SQLite отдельно от стенда. | Адаптер чтения цепочки по TraceRef и адаптер фиксации выборки по run_id. Для тестов подставляется время окончания сбора. |
| Амир | Готовые метаданные и выборки двух прогонов, плюс пример конфига. Проверяет расчёт и API без работающих сервисов и OTLP. | Диагностика, намерение изменения и сравнение. Проверяет равенство сценария, нагрузки и сбоя, отличие одного поля и статус выборок. |
| Хамза | Общие JSON-примеры API, включая 403, 409, stopping, waiting и partial. | Интерфейс, который можно проверить на моках. При подключении меняется API-клиент или источник его ответов. |

Минимальные внутренние стыки внутри одного Python-приложения:

- **Миша → Никита.** Вход TraceRef. Выход содержит исходный TraceRef и упорядоченные вызовы с ключами caller/callee, операцией, наблюдаемым статусом и длительностью. При неполной цепочке возвращается причина. Например, один вызов из orders в payment с HTTP 200 и длительностью 350 мс. Неизвестные параметры конфига дополняет Никита.
- **Никита → Миша.** Метка run_id в OTLP и задание зафиксировать выборку с ожидаемым числом запросов и сроком сбора. Миша возвращает run_id, status, expected_count, received_count и список точных TraceRef. При повторном чтении набор ссылок остаётся тем же.
- **Никита и Миша → Амир.** Никита даёт run_id, stand_id, ревизии сценария и сбоя, параметры нагрузки и снимок конфига. Миша даёт зафиксированные ссылки и модель наблюдаемых попыток. Базовый тестовый пример P11 — одинаковые нагрузка и сбой, max_attempts 3 и 2.
- **Амир → Никита.** Recommendation ID, occurrence ID, цель service_id/call_ref, ожидаемая ревизия и изменение одного поля. Для теста применяется max_attempts 2. Никита самостоятельно проверяет, что цель на стенде, поле разрешено и ревизия актуальна.

## 4. Телеметрия и данные

- `POST /v1/traces` принимает OTLP/HTTP protobuf. Токен источника определяет окружение на сервере. Продуктовый API управления доступен локальному оператору.
- Запись идёт транзакцией. Успешный ответ отправляется после commit. Повтор одного пакета не удваивает спаны. Поздний спан обновляет текущую ревизию, сохраняя ссылки на использованные снимки.
- Идентификатор трассы в продукте включает окружение, trace ID, generation и revision. Генератор стенда и сравнение читают точные ревизии. Фиксированные выборки остаются доступны в течение срока хранения прогонов. Если данные удалены по политике хранения, API сообщает об этом явно.
- Лабораторный генератор присваивает каждому входному запросу run_id и отдельный trace ID. Каждая попытка выполняется отдельным HTTP-вызовом и создаёт отдельный клиентский спан в той же трассе. Никита добавляет лабораторные метки logical_call_id и attempt_index, Миша группирует по ним. Для внешних трасс без этих меток Амир показывает только подтверждённые наблюдения. Пробный запрос имеет отдельную метку и исключается из выборок.

## 5. Конфигурация и рекомендации

- Для чтения и записи сервер находит сервис по идентификатору в выбранном окружении и проверяет зарегистрированный адаптер и конкретное поле. Таймаут исходящего вызова принадлежит вызывающему сервису.
- Ручное изменение и рекомендация используют общий механизм «план → подтверждение → запись → проверка фактического значения». Источник действия хранится в плане. План из рекомендации для внешнего окружения отклоняется с `403 recommendation_lab_only` при создании и применении.
- План связан с целью и ожидаемой ревизией. Устаревшая ревизия даёт `409 stale_revision` без записи. Один request_id соответствует одной операции. Перед отправкой изменений сохраняется запись журнала. Если подтверждение потерялось, статус остаётся unknown до сверки с адаптером.
- Для наблюдаемых повторов показываем размер пригодной выборки и основание группировки попыток. R4 получает известный конфиг и рассчитывает бюджет. Значения 850 и 550 мс подписываются как расчёт по политике. Измеренная длительность показывается отдельно. При недостаточных данных аудит показывает соответствующий статус.

## 6. Жизненный цикл стенда

1. **Сборка.** Checkout стенд создаётся по `scenario_id`; готовый сценарий поддерживает serial и parallel группы. A резервирует слот и запускает девять процессов, проверяя readiness. Текущий build deadline — 20 секунд. При timeout API возвращает stand_build_timeout, слот удерживается до очистки. При потерянном POST ответе UI сверяет состояние через GET active; частично запущенные процессы очищаются.
2. **Запуск.** Сервер под общей блокировкой сверяет scenario/fault revisions и карту revision всех сервисных конфигов, затем создаёт run_id и сохраняет request_id. Запрос задаёт число запросов, concurrency и optional seed; повтор с тем же телом идемпотентен. Во время нагрузки конфиг/fault edits, остановка и второй запуск получают `409 run_in_progress`.
3. **Сбор результатов.** После прекращения нагрузки прогон может быть completed, пока сбор трасс остаётся waiting. Никита задаёт срок ожидания до 20 секунд. Модуль Миши проверяет полноту трасс и к сроку фиксирует выборку как ready или partial. Поздние трассы видны отдельно. Уже зафиксированная выборка сохраняется для повторного сравнения.
4. **Остановка.** Пока выборка не зафиксирована, остановка возвращает `409 traces_pending`. После фиксации сервер переводит стенд в stopping, корректно завершает процессы и подтверждает stopped после освобождения ресурсов. Если остановка не подтверждена, слот остаётся занятым, разрешён повтор DELETE.
5. **Перезапуск.** Супервизор восстанавливает записи о стенде и операциях. Незавершённая нагрузка помечается failed. Бэкенд очищает только процессы, принадлежность которых старому стенду подтверждена. До завершения очистки слот не освобождается. Завершённые прогоны и журнал сохраняются.

## 7. Сравнение и приёмка

Сравнение проверки рекомендации принимает два разных run_id одного стенда. Ревизия сценария, параметры нагрузки и ревизия сбоя совпадают. В снимках конфигурации отличается одно проверяемое поле. Несопоставимые прогоны возвращают `422 runs_not_comparable` с причиной. Неполная выборка показывает полученное и ожидаемое число трасс.

Общий прогон команды:

- [ ] Внешние и лабораторные трассы раздельны. Повтор OTLP-пакета не удваивает статистику.
- [ ] Полная внешняя трасса строит стенд. Неполная цепочка даёт понятную причину отказа.
- [ ] Ручная запись разрешённого поля внешнего `orders` подтверждается чтением. Применение рекомендации к тому же внешнему сервису получает 403.
- [ ] Повтор запуска с тем же request_id возвращает тот же run_id. Устаревшая ревизия не запускает нагрузку. Остановка активного прогона и ожидание трасс дают разные ошибки.
- [ ] При одинаковом сбое и нагрузке лимит меняется с трёх попыток до двух. В каждой полной трассе видно три отдельных попытки до и две после, а ответ `503` сохраняется.
- [ ] После остановки порты освобождены, трассы и журнал читаются. После перезапуска незавершённый прогон не запускается повторно.

Первый интеграционный результат: запустить checkout-сценарий, выполнить faulted run и увидеть его OTLP-трассы; затем повторить при изменённой конфигурации и сравнить сохранённые выборки. Генерацию стенда из внешней трассы подключать отдельным этапом.

## Актуальное решение: явные JSON-сценарии (12.11.2026)

Этот пункт заменяет прежнее создание/восстановление стенда по трейсу. Поддерживаются два входа: заранее заданный `lab_scenario_file` окружения и загрузка JSON в лаборатории. Общие серверная проверка, нормализация, неизменяемый SHA-256 снимок в SQLite и исполнитель. Отдельные исполнения шага имеют разные logical_call_id, повторы одного исполнения — общий. Seed сохраняется в результате и доступен для повторного использования. История сохраняется, новый стенд берёт настройки только из JSON.

UI: общая кнопка загрузки файла и сводка перед созданием, без textarea, технического описания parallel и подписи о трёх сервисах. Единые отступы; плашка «Проблем: N» в заголовке аудита удалена. Прогноз ускорения и сравнение тестов не возвращать.

Контракт и ограничения: [сценарии стенда](../guides/lab-scenario.md).
