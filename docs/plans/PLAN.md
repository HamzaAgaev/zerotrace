## 2. Что уже определено

- Один ZeroTrace и один Python-бэкенд. Внешняя система и лабораторный стенд отправляют реальные трассы OTLP в общий конвейер. Мониторинг охватывает всю наблюдаемую цепочку. Права чтения и изменения конфига включаются отдельно для каждого сервиса с поддерживаемой интеграцией.
- Подключение наблюдения — без изменения исходного кода приложений. Можно установить готовый языковой агент/пакеты и изменить команду запуска или переменные окружения. Это не обещание подключения вообще без настройки/перезапуска. Ограничения «только Go» нет.
- Один Python backend. Готовый внешний агент и Collector могут быть написаны на другом языке.
- Linux не является зависимостью продукта. Целевые ОС backend/CLI: Windows, macOS и Linux; контейнеры и eBPF — дополнительные профили.
- Команда: D — один фронтендер, A/B/C — три бэкендера. A дополнительно отвечает за инфраструктуру.
- Команда — четыре человека; первая демонстрация через 2–3 дня.
- Нормализованный граф спанов сохраняем, весь доступный поток разрешено обрабатывать до отбора.
- Для внешнего сервиса доступны чтение конфига и ручное редактирование при соответствующих правах. Рекомендации видны и во внешней системе, и в лаборатории. Кнопка «Применить рекомендацию» действует только на стенде. В лаборатории также доступны задержки, HTTP-ошибки и повторяемые прогоны. Никита ведёт серверный API и адаптеры, Хамза — интерфейс.

**Рабочий выбор для первого показа.** Flask+requests с языковой автоинструментацией OpenTelemetry. Начинаем с одной машины и отдельно фиксируем проверенные ОС. Во внешнем окружении показываем наблюдаемые повторы при подтверждённой группировке попыток. На стенде используем R4 по известной конфигурации. Точные стыки и сценарий описаны в P11. Ответы на предыдущие вопросы не означают автоматического принятия этих деталей.

## 3. Что строим

Инструмент получает связанные HTTP-трассы, показывает цепочку вызовов, обнаруживает опасную конфигурацию retries/timeouts, объясняет расчёт и предлагает конкретное изменение. Если подключён поддержанный адаптер управления, пользователь может применить изменение и увидеть подтверждение новых настроек и доступные наблюдения после него.

Анализатор не ограничен языком приложения: его вход — OTLP. Поддержка конкретного источника зависит от runtime, библиотек, протоколов и ОС; публикуем проверенную матрицу. Backend может принимать traces от удалённых источников на другой ОС. OBI/eBPF остаётся необязательным Linux-источником, не частью обязательного запуска.

В прежнем Rust Retry Auditor кнопка «Применить» отправляла патчи в специальный `/_config` собственного стенда. Настройки произвольных подключённых приложений она не меняла. Внешний агент наблюдения сам по себе не является способом менять конфиги retries/timeouts.

### Полная целевая функциональность

| Подсистема | Что должна уметь | Основание в исходных проектах |

Эксперимент меняет условия на стенде и собирает новые трассы. What-if отдельно рассчитывает прогноз по сохранённой трассе. Согласованный срез первого показа и его границы описаны в [configuration-and-lab.md](../architecture/configuration-and-lab.md). В первом показе Docker Compose — основной путь разработки и запуска; по умолчанию запускается backend/UI, а профиль `demo` добавляет девять приложений и `demo-load`. Полная нативная переносимость backend/CLI на Windows, macOS и Linux остаётся целевой целью продукта и не считается проверенной в рамках этого решения. Готовый checkout задаётся сценарием с последовательными и параллельными группами; лабораторный стенд можно собрать напрямую по `scenario_id`, без предварительной внешней трассы. Генератор из трассы реализован с сохранением ветвлений, параллельных вызовов и повторов.

Первый режим R4 — **config-aware**: таймауты и число попыток явно прочитаны из настроек. Нельзя показывать их как выведенные из трасс. Сами трассы подтверждают наблюдаемую связь и вложенность. Отсутствие timeout-аннотации не превращается в известный настроенный timeout.

## 5. Архитектура

```text
Наблюдаемые приложения
  → языковой агент / существующий OTLP / необязательный eBPF → OTLP/HTTP
  → B: декодирование → нормализация → SQLite → граф/попытки/качество
  → C: политики + аудит → находки + рекомендации + намерения
  → C: аналитические API/Snapshot/отчёты → D: UI
  → B: API данных → D: UI

A: независимый стенд, нагрузка, конфигурационный API, fixtures
  ├→ агент → B
  └← A: control API/adapters/journal ← D: показать план и отправить действие

Сохранённый граф → будущие what-if и сравнение групп
```

B и C содержат чистые вычислительные функции. Сеть и операции принадлежат серверным модулям A/B/C; SQLite — B; D отвечает за клиентский интерфейс. Состояние приложения отделено от чистой аналитики. Физически backend один; выделять каждый модуль в отдельный сервис не нужно. A не импортирует аналитические модули и не сообщает анализатору скрытое место сбоя.

Сохраняем граф на диске, а не только таблицу попыток. Для первого bounded-датасета допустим полный пересчёт: сложный инкрементальный конвейер не должен задерживать первый срез. Дедупликация, ограничение памяти и корректная запись обязательны.

Для полной системы граф порождает две независимые проекции: CallModel для аудита и IntervalModel для what-if. Общие операции над интервалами переиспользуются, но суммы расходов, гипотезы ретраев и причинные предположения не смешиваются. What-if не является симуляцией изменения retries/timeouts.

A владеет app/server: запуск HTTP-сервера и подключение роутеров B/C. Это один backend process, не три сервиса. A не реализует вместо коллег их обработчики. B задаёт storage-интерфейсы; A пишет control/journal business layer, C пишет analytics business layer. Схемы общие, их ревьюят производитель и потребитель.

У каждого backend API один ответственный; frontend работает по fixtures/OpenAPI и не ждёт готовности сервера. D показывает арифметику, но C вычисляет её; D показывает журнал, но A хранит и исполняет операции; D показывает дерево, но B строит его.

A пишет независимые scenarios/expected. C пишет scorer, не подгоняет expected под правила. C не перегружается инфраструктурой, а D — серверной логикой. Infra — закреплённая часть роли A, а не пятый участник.

## 7. Платформы и подключение

**Продукт:** Python backend/CLI и браузерный UI должны запускаться на Windows/macOS/Linux нативно, без обязательных Docker, Linux VM, root или kernel modules. Целевые ОС — требование к реализации, а не утверждение, что они уже проверены. SQLite на локальном диске. Контейнерный профиль остаётся дополнительным.

**Источники:** (1) существующий OTLP/файл, (2) языковая автоинструментация/агент через настройки запуска, (3) необязательный OBI/eBPF там, где доступен. Ни один конкретный агент не обязателен для старта backend. Не обещаем одинаковые атрибуты и поддержку каждого framework на каждой ОС.

Кандидат первого стенда — Flask+requests через opentelemetry-instrument, без ручных spans/SDK-вызовов в исходниках. Требуется установка инструментирующих пакетов и настройка запуска; этот факт виден в инструкции. Для Java/Node.js/.NET добавляются отдельные проверенные профили. Собственный SDK-код в лаборатории допустим как дополнительный oracle, не как замена заявленной автоинструментации.

Первые 2–4 ч A+B проверяют доступный профиль на машине разработчика: общая trace_id, client/server/parent связи под конкуренцией, method/operation/target/status/duration и реальные сигналы errors/retries. A отвечает за инструменты/запуск, B — за пригодность данных. Не нужен отдельный Linux gate для всего продукта.

В первый показ стремимся включить native smoke на двух доступных ОС; если доступна одна — не объявляем остальные проверенными. До полной кроссплатформенной приёмки CI проверяет backend/CLI на всех трёх ОС, а реальные источники имеют отдельную матрицу.

В native-коде не использовать обязательные bash/Make, Unix signals, fork, /proc, systemd, Unix sockets, жёсткие /tmp paths или Linux-only event loop. Переносимые Python entrypoints/pathlib/subprocess, штатная остановка HTTP/process API, optional platform adapters. Docker/Linux-specific сценарии изолированы.

Основание выбора языковых вариантов: [OpenTelemetry zero-code](https://opentelemetry.io/docs/zero-code/), [Python auto-instrumentation](https://opentelemetry.io/docs/zero-code/python/), [Java agent](https://opentelemetry.io/docs/zero-code/java/agent/). Поддержку конкретных ОС/библиотек подтверждает матрица A, не само наличие этих страниц.

## 9. Общие инженерные правила

1. Время внутри — целые наносекунды, ID — lowercase hex; JSON ns — десятичные строки.
2. Значение имеет источник. Unknown отличается от нуля, false и «ошибок нет».
3. Повторная доставка не удваивает спаны/счётчики. Поздние спаны дополняют trace, меняют revision и инвалидируют результат.
4. HTTP-успех приёма — после commit. Ошибка записи не подтверждается как приём.
5. CLIENT и SERVER статус не смешиваются; clocks разных хостов не вычитаются без основания.
6. «Настройки применены» и «симптом не наблюдается» — разные статусы. Архив после apply не очищается.
7. Применение — по явно настроенному адаптеру и конкретному плану, не по адресу из импортированного span.
8. Bounded RAM, лимиты пакета/trace и явный отказ при перегрузке обязательны.

## 11. Готовность и открытые решения

Готовность первого показа: оба внешних сервиса видны в одной цепочке, настройки доступны у поддерживаемой цели. На стенде оператор задаёт задержку или HTTP-ошибку, применяет рекомендацию с проверкой версии конфига и повторяет прогон. Интерфейс показывает новые трассы и наблюдаемые изменения. Журнал переживает перезапуск, ошибки записи и конфликты видны.

Перед общей интеграцией A и B проверяют выбранный профиль на реальном OTLP-пакете. Если нужных признаков повторов нет, C показывает недостаточность данных. Команда сверяет API по примерам P11 и проверяет лабораторный сценарий сквозным прогоном. Полные TTL/бюджеты, удалённый доступ, дополнительные языки и адаптеры остаются дальнейшими решениями. Этот комплект сам по себе не является разрешением начать реализацию.

В проверку M3 включить отзывчивость под живым потоком OTLP. Список, карточка и граф получают телеметрию отдельно от аудита. На вычисление аудита выделяется фоновая задача, а браузер проверяет готовность короткими запросами с лимитом 5 секунд. Проверять холодный и повторный запуск, параллельный приём спанов и сохранение точных TraceRef.

## 13. Ключевые архитектурные решения

- **Хранить граф:** планы rewrite удаляли spans после Attempt; это уничтожает what-if и повторный анализ. Граф на диске, RAM-кэш ограничен.
- **Общий timing через union:** Rust суммировал длительности пересекающихся calls; исправляем двойное вычитание. Время вне direct children и вне outgoing calls — отдельные показатели.
- **Ревизии:** поздний span меняет проекции; contribution trace заменяется, а не прибавляется. Call ID не обещает стабильность между ревизиями.
- **Sampling после аналитики:** tail-selected архив не источник здоровой базы и population error ratio.
- **Качество по алгоритму:** непригодный what-if не обязан скрывать все HTTP-наблюдения; unknown не превращается в нулевой выигрыш.
- **Контроль отдельно:** typed intent не произвольный patch/команда; адрес управления из trusted config. Наличие агента не даёт контроля над приложением.
- **Наблюдение/гипотеза/прогноз/измерение:** четыре явно подписанных типа результата; не общий «доказанный диагноз».

## 14. Готовность полной системы

Все функциональные строки раздела3 реализованы либо имеют явно согласованное исключение; все стыки P1–P10 проходят fixtures. Аудит и what-if используют одни исходные refs, но свои quality gates. Отчёт воспроизводим по версиям. Совместный gain не суммируется из строк рейтинга. Cohorts описательны. Apply не выдаёт исчезновение finding за исправление причины. Ошибки/потери/limits видны. Есть native запуск/CI на Windows/macOS/Linux и независимые измерения на стенде; совместимость источников опубликована отдельно.

Retry Auditor: `crates/otlp-model/src/lib.rs`, `crates/auditor/src/{calls,edges,chain,timing,rules,recommend,live,eval,report}.rs`, `crates/stand/`, `scenarios/`, `docs/rewrite/`. ZeroTrace: `autopilot/internal/autopilot/{otlp,model,retention,search,analysis,compare,application,capture}.go`, соответствующие тесты, `cmd/reportlab`, `lab/validate.py` и текущая SPECIFICATION.

Это поведенческие источники, не команда копировать код. Исходные языки Rust/Go не определяют язык новой системы. При расхождении со старым кодом проверяем смысл и oracle: union, client-status, sampling, ambiguity и ревизии требуют осознанных исправлений, а не побайтного повторения старых результатов. Старые документы про zero-code/прокси не считаются доказательством уже реализованной функции.

### Независимость от предметной области — решение 12.11.2026

ZeroTrace — внешняя система наблюдения и анализа уже существующих сервисов независимо от их назначения. Магазин/checkout — исключительно демонстрационный набор, не основной сценарий продукта. Основной вход в лабораторию: выбрать трейс подключённой системы и создать по нему тестовую модель. Готовый пример выделен отдельным действием «Запустить демонстрационный стенд».

Текущие ограничения, которые нельзя скрывать текстами интерфейса:
- Генератор из трейса сохраняет ветвления, параллельные группы и каждую наблюдаемую попытку с её вложенными вызовами. Это модель вызовов, не копия бизнес-логики приложения.
- Изменение конфигурации внешних сервисов требует поддержанного адаптера; получение телеметрии само по себе не даёт такой возможности.
- Значения shop/sandbox и реестр управляемых сервисов требуют отдельной проверки и устранения неявных подстановок в продуктовом подключении. Существующее подключение не менять автоматически.
- Приёмочные сценарии должны включать сервисы с другими именами и эндпоинтами, без checkout/orders/payment.


## Решение 12.11.2026: убрать сравнение тестов

Сравнение тестов временно удалено из интерфейса тестового стенда, включая выбор тестов до/после и таблицу сравнения. Остаются запуск нагрузки, история результатов и переход к трейсам. Это решение заменяет прежние пункты о сохранении сравнения в лаборатории. Серверный API сравнения пока сохраняется; возвращение функции требует отдельного решения.


## Понятные результаты и настройки тестового стенда — 12.11.2026

У каждого теста отдельный экран #/lab?run=ID. После запуска он открывается автоматически и обновляется до завершения сбора трейсов. Показаны успешные запросы, HTTP/сетевые ошибки, медиана и 95-й перцентиль полного времени запроса, распределение ответов и времени, все доступные ссылки на трейсы. Метрики рассчитаны по сохранённым результатам генератора нагрузки, независимо от полноты телеметрии; неизвестные результаты не считаются успешными. Старые тесты без подробных результатов показывают явное сообщение. Демостатистика явно обозначена как симуляция. Сравнение тестов не возвращается.

В стенде кнопка «Сохранить настройки» готовит и применяет план внутри приложения без модального окна, с контролем версии и повторным использованием идентификатора операции при неопределённом ответе. Внешние сервисы сохраняют предварительный просмотр изменений («Посмотреть изменения»). Обработка, вызовы зависимостей и имитация ошибок разделены вкладками; убраны внутренние линии и унифицированы отступы. История запусков ведёт к результатам, а не к случайному первому трейсу.


## Ошибки и повторы в результатах теста — 12.11.2026

В результатах теста добавлена статистика сервисов по точным TraceRef собранной выборки. Ошибки (HTTP 4xx/5xx, OTel error, error_type) учитываются независимо от результата корневого запроса. Сервисом считается владелец спана; повторы относятся к инициатору клиентского вызова и определяются только по attempt_index > 1 или resend_count > 0. Одинаковые названия операций не служат доказательством повтора. Для каждого сервиса отдельно доступны списки трейсов с ошибками и повторами; один трейс учитывается один раз. Недоступные версии и неполный сбор явно обозначаются. Демо без сохранённой телеметрии не выдаёт выдуманные ошибки и ссылки.

### Графики периода и таблицы
- Трейсы: динамика доли ошибок, медианы и 95-го перцентиля основного запроса по всей системе, 12 интервалов выбранного периода. Пустые интервалы не подменяются нулём.
- Сервисы: распределение полного времени обработки выбранного эндпоинта за выбранный период. Демо и сервер используют одинаковые интервалы и общий компонент гистограммы с результатами теста.
- Все таблицы используют общие цвета заголовков, границ и подсветку hover/focus-within. Курсор указателя только для строк с действием.

- Графики на странице трейсов скрыты по умолчанию и открываются кнопкой рядом с периодом. Подписи-инструкции под графиками убраны; значения доступны в подсказках точек. Главная задача страницы — поиск трейсов.

- Настройки подключения доступны напрямую в основном меню. Раздел «Ещё» и его разделитель удалены.

## Актуальное решение: явные JSON-сценарии (12.11.2026)

Этот пункт заменяет прежнее создание/восстановление стенда по трейсу. Поддерживаются два входа: заранее заданный `lab_scenario_file` окружения и загрузка JSON в лаборатории. Общие серверная проверка, нормализация, неизменяемый SHA-256 снимок в SQLite и исполнитель. Отдельные исполнения шага имеют разные logical_call_id, повторы одного исполнения — общий. Seed сохраняется в результате и доступен для повторного использования. История сохраняется, новый стенд берёт настройки только из JSON.

UI: общая кнопка загрузки файла и сводка перед созданием, без textarea, технического описания parallel и подписи о трёх сервисах. Единые отступы; плашка «Проблем: N» в заголовке аудита удалена. Прогноз ускорения и сравнение тестов не возвращать.

Контракт и ограничения: [сценарии стенда](../guides/lab-scenario.md).
