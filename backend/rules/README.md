# Входы и результаты P5

`run(model, policies, thresholds=None, baselines=None)` обрабатывает одну зафиксированную выборку. Результат содержит `findings`, статусы и исключения каждого правила, наблюдения по рёбрам, версии и ссылки на входы. `get_recommendation(result, occurrence_id, recommendation_id)` извлекает предложение из конкретного результата. Для используемых фронтендом ответов адаптер находится в `app/analytics_api/`.

**Доверие к политике.** Чтение операндов конфигурации (свежесть снимка,
источник, сверка ревизий) делегировано каноническим примитивам зоны B —
`core/model.py` (`build_edge_policy`, `trusted_int`, `sourced_value`,
`is_current_policy`, `pauses_ns`). Здесь семантика определена однажды;
поведение правил зафиксировано golden-снимками
`fixtures/analytics/golden/` (тест `tests/analytics/test_migration_golden.py`).


**Данные Миши.** В `model` обязательна строка `environment_id`. Передавайте также `dataset_ref`, `model_version`, `sampling`, точные ревизии трасс, `attempts` и `calls`. Каждый Attempt имеет `trace_ref`, `attempt_id` клиентского спана и `edge_id`. У LogicalCall обязательны `trace_ref`, `edge_id`, `call_id`, упорядоченные `attempt_ids`, `hypothesis` и `confidence`. Подходят подтверждённые single и retry. Диагностика качества распространяется по затронутым ссылкам и на весь граф для ошибок без области. Источник может отдать attempts/calls внутри соответствующей трассы. Машинные ключи рёбер и их подписи передаются раздельно.

**Данные Никиты.** `policies` содержит P4 snapshots с `edges` либо уже разрешённые политики одного ребра. Для R4 нужны `execution="serial"`, `source` (runtime или declared), `config_revision`, `max_attempts`, `per_attempt_timeout_ns`, локальный `budget_ns`, `backoff` с видом паузы, длительностью и типом jitter. Снимок P4 передаёт владельца в `service.service_name` и ревизию в `revision`. Внешний таймаут из списка `external_timeouts` подходит при единственном точном совпадении по `call_ref`. Числовые параметры поддерживают `{value, source, config_revision, stale}`. Явно устаревшие и несовместимые по ревизии значения исключаются. Ссылка на целевое поле требует `service_id` и `call_ref`; исполнимое намерение дополнительно требует `model.environment_kind="lab"`, совместимого типа окружения и разрешения на поле в capabilities.

| Правило | Используемые входы |
|---|---|
| OBS_RETRIES | Подтверждённые LogicalCall, отдельные уникальные CLIENT attempts. Отдельно публикуются знаменатели по логическим вызовам и трассам. |
| R1 | Ошибочный клиентский исход, `duration_ns`, связанный `server_span_id` и `server_duration_ns`, пригодность пары. Необязательная здоровая база используется для гипотезы деградации. |
| R2 | `upstream_attempt_id`, совпадение `caller_server_span_id` с SERVER upstream-попытки, длительность ожидания и `offset_in_caller_ns`, вычисленный B на совместимых часах. |
| R3 | Подтверждённые вложенные группы, связи по upstream и server IDs, `first_path` на потомках. Теоретический предел отдельно требует известных последовательных лимитов каждой политики пути. |
| R4 | Настройки попытки и бюджета из одной области и ревизии. Учитываются известные `reserve_ns`, `elapsed_ns` и ограничения `healthy_duration_ns`, `min_timeout_ns`. |
| R5 | Для паузы между двумя CLIENT-попытками нужны подтверждённая retry-группа, числовой интервал и общий известный `clock_domain`. Пригодные паузы агрегируются отдельно по номеру попытки. |
| R6 | HTTP method группы/попытки или нормализованной операции клиентского спана и наблюдаемый `idempotency` по каждой попытке записи. |
| R7 | CLIENT HTTP/gRPC-статус попытки, за которой следует подтверждённый повтор. Для gRPC требуется заявленная политика retry_on, для HTTP доступен default из контракта. |
| R8 | Известные `per_attempt_timeout_ns` и `upstream_per_attempt_timeout_ns` сопоставимой пары. |
| D1 | Источник и значения настроек, сегмент и ревизия, подтверждённые группы попыток, при достаточном покрытии — отдельная оценка таймаута по клиентским timeout-исходам. |

Версия правил 1.1 проверяет единственную ревизию каждой generation трассы в пределах среза. Противоречащий TraceRef у вложенного вызова делает вход непригодным. В P4 общий снимок определяет владельца, ревизию и доступные поля записи. Строка отдельного ребра может сузить разрешения. Противоречие идентичности или исторической ревизии исключает применение.

При наличии графа R1–R3 сверяют нормализованную привязку с ancestry CLIENT/SERVER, допуская промежуточные INTERNAL. R3 включает в знаменатель подтверждённые вложенные цепочки с известным первым путём, в том числе без повторов, и выбирает глубочайшее затронутое ребро каждой ветви. Оценка приоритета P5 использует severity, confidence и долю в пригодной выборке по контракту §10. При отсутствии знаменателя `score=null` и причина находится в `score_reason`. Проверка симптома сравнивает версию правила и набор порогов между прогонами.

## Политика сопоставления D1

Сегмент сравнения содержит окружение, ребро, версии вызывающего сервиса и получателя, нагрузку и ревизию настройки. Для сравнения runtime и declared требуются также один владелец и один `call_ref`. Передавайте два отдельных снимка или две строки политики одного ребра. D1 сохраняет значения обоих источников и показывает точное различие в `max_attempts` или `per_attempt_timeout_ns`. Консервативная стратегия текущей реализации оставляет выбор управляющего снимка за интеграционным слоем: при нескольких снимках на одно ребро R4 не выпускает исполнимую рекомендацию. Несколько различных значений одного источника считаются конфликтом.

Максимум подтверждённых попыток — наблюдаемая нижняя граница. Для времени используется отдельная оценка. A/B явно маркируют область таймаута `timeout_scope="per_attempt"`; метка может быть общей для выборки либо относиться к конкретной трассе, вызову, попытке. Используются только CLIENT attempts с `outcome="timeout"`, положительной длительностью и согласованными версиями/нагрузкой/ревизией. Эти измерения принимаются при `sampling={"mode":"all_received","known_losses":false}` и как минимум `min_cases` различных трасс (по умолчанию пять). Успехи, deadlines родителя и другие исходы исключаются с причиной. Смешение версий и неизвестные потери блокируют оценку.

Центр кластера — медиана в наносекундах. Размах max−min должен укладываться в максимум из абсолютного допуска (20 мс) и `cluster_spread_relative × median` (10% по умолчанию). Сравнение с конфигом срабатывает, когда весь диапазон выходит за пределы настроенного значения с допуском `max(tolerance_ns, timeout_drift_relative × configured)`. Это эвристика с уровнем уверенности medium. `observations[].policy_evidence` содержит источник, конфигурационные значения, min/max, медиану, численность и причины исключения. Поля `value_ns` и `comparison_tolerances_ns` доступны для пригодного кластера. Допуски настраиваются через `load_thresholds`, в том числе по `edge_id`.

## Reference baseline и verification

`build_reference(segment, attempts, sampling, version=..., created_at=..., valid_until=...)` строит явно версионированную здоровую базу по одному сегменту. Сегмент содержит `environment_id`, `edge_id`, `caller_version`, `callee_version`, `workload_id`. Метаданные задают источник, окно, число наблюдений, долю ошибок, минимум, максимум и p50/p95/p99 длительностей успешных попыток. Аудит получает такие базы через `baselines`; актуальность проверяется на момент `model.generated_at` (RFC3339 UTC). Новый reference создаётся явно. Автоматического обучения на входящем потоке нет. `verify_symptom` возвращает статус для конкретного срабатывания после проверки среды, сопоставимости, покрытия и количества вызовов соответствующего ребра. Расписание проверки и журнал принадлежат модулю управления.
