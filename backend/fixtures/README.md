# fixtures

**Зачем:** эталонные примеры данных с контрольными числами. На них все
участники проверяют свой код независимо, не дожидаясь чужих модулей:
Хамза рисует UI, Амир проверяет аудит, Миша сверяет свой построитель
графа и группировку попыток. Зона B (Миша).

**Как устроено:** файлы НЕ правятся руками — генерируются скриптами,
наносекунды и числа считает код, любой может пересобрать:

```sh
python3 fixtures/build_model_fixtures.py   # model-фикстуры
python3 fixtures/build_otlp_fixtures.py    # OTLP/JSON пакеты
```

- `model/` — контрактные `TraceGraph` + `CallModel`: `s00_healthy`
  (один вызов orders → payment, HTTP 200) и `s01_retry` (503 + 3 попытки
  по 250 мс с паузами 50 мс = 850 мс — совпадает с арифметикой R4 из
  плана демо), плюс `run.json` со связкой run_id ↔ TraceRef.
- `otlp/` — те же трассы в OTLP/JSON формате (вход для decoder-тестов):
  `s00_healthy`, `s01_retry`, `late_duplicate` (повтор пакета и поздний
  parent).
- `product/` — реальные ответы data API (списки и детали трасс по
  окружениям), собранные сквозным прогоном конвейера; фронтенд разрабатывает
  против них до поднятия сервера.

Правило изменения: контрольные числа меняются только с причиной и
ревью потребителей fixture; тесты совместимости с фронтендом читают
`frontend/fixtures/frontend-contracts.json`.
